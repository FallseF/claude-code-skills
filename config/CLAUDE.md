## eval モード

ユーザーがメッセージの文末に `eval` と記載した場合、以下のルールに従うこと：

- ユーザーに忖度しない
- プロンプトや提案内容をフェアかつ客観的に評価する
- 問題点、改善点、リスクがあれば遠慮なく指摘する
- お世辞や過度な肯定は避け、正直なフィードバックを優先する

## askif モード

ユーザーがメッセージの文末に `askif` と記載した場合、以下のルールに従うこと：

- すぐに実行せず、まず確認・追加質問を行う
- 曖昧な点、前提条件、考慮すべき選択肢を洗い出して質問する
- ユーザーの意図を正確に把握してから作業に着手する
- 「これでええんか？」「こういうケースも考慮するか？」等の確認を優先する

## 並列エージェント作業時のルール（git worktree）

複数のエージェントが同時に別ブランチで作業する場合、**必ず git worktree を使用**すること。

### なぜ必要か
- 同じディレクトリを複数エージェントが共有すると、`git checkout` が競合してブランチが入れ替わる
- 各エージェントが独立したワーキングディレクトリで作業すれば、この問題を回避できる

### worktree の基本操作

```bash
# 新規ブランチでworktree作成
git worktree add ../project-feature-name -b feature/feature-name

# 既存ブランチでworktree作成
git worktree add ../project-feature-name feature/existing-branch

# worktree一覧
git worktree list

# worktree削除（作業完了後）
git worktree remove ../project-feature-name
```

### 作業時の注意
- 指定されたworktreeディレクトリ内でのみ作業する
- メインリポジトリで `git checkout` を実行しない
- 作業完了後、PRマージ後にworktreeを削除する
- git worktreeの作成を依頼された場合、`git branch`ではなく`git worktree add`を使用すること。ブランチとworktreeの違いを常に確認すること

### 指示を受ける側のエージェントへ
- 作業ディレクトリが明示されていない場合は確認すること
- 他のworktreeディレクトリには絶対に触れないこと

## Git 運用ルール

### 禁止事項
- `main` / `master` ブランチへの直接 push 禁止（必ずPR経由）
- `git push --force` 禁止（`--force-with-lease` も原則禁止）
- `git reset --hard` を共有ブランチで使用禁止
- 機密情報（APIキー、パスワード等）のコミット禁止

### ブランチ命名規則
```
feature/機能名     # 新機能
fix/バグ内容       # バグ修正
refactor/対象     # リファクタリング
docs/対象         # ドキュメント
test/対象         # テスト追加
```

### コミットメッセージ
- 日本語または英語で簡潔に（50文字以内推奨）
- 何をしたかではなく、なぜしたかを意識
- 例: `Add user authentication for security` / `ユーザー認証を追加`

### PR作成時
- タイトルは変更内容を簡潔に
- 説明には「何を」「なぜ」「どうやって」を含める
- 関連するIssue番号があればリンク

## コードスタイル

### 一般原則
- プロジェクトの既存スタイルに従う（郷に入っては郷に従え）
- Linter/Formatter の設定があれば必ず適用
- 不要なコメントアウトは残さない
- console.log 等のデバッグコードは残さない

### 変更時の注意
- 関係ない箇所のリファクタリングを混ぜない
- 1つのPRには1つの目的（Single Responsibility）
- 大きな変更は分割して段階的にPR

## 開発サーバー

- devサーバー起動前に、対象ポートで既に実行中のサーバーがないか確認すること（`lsof -i :<port>` or `ps aux | grep`）。既存プロセスを停止してから新しいサーバーを起動

## 問題解決

- ライブラリやツールの統合がうまくいかない場合、カスタムソリューションにフォールバックする前に根本原因を徹底的にデバッグすること。ユーザーの選択したアプローチを明示的な許可なく放棄しないこと
- 大規模なリファクタリングや複数ステップの機能実装の場合、コードを書く前にまず計画を提示してユーザーの承認を得ること。計画が確認されるまでコーディングを開始しないこと

## 図表・可視化

- 論文品質の図表にはNatureスタイルのデフォルト（クリーン、ミニマル、ハイコントラスト）を使用。データの正規化時は、スケールやエッジケース（オフ領域の比率、補間の順序）をレンダリング前に検証すること
- 日本語テキストを含む図表を生成する際は、日本語対応フォント（IPAexGothic、Noto Sans JPなど）を使用し、レンダリングを確認すること

## コード標準

- TypeScriptを主要言語として使用。明示的に指示されない限り、新規ファイルは常にTypeScript（JavaScriptではない）で書くこと。タスク完了前に型の正確性を確認すること

2. 変更したファイル一覧
3. テスト結果（実行した場合）
4. 注意点・残課題（あれば）
