# goal-creater: 実装担当モデル向けリファクタ指示書の生成

Claude Code 以外（Codex 等）で使う場合は、AskUserQuestion などの道具をその環境の同等品に読み替える。AskUserQuestion が無い環境では、ユーザーに聞いて止まる。

対象プロジェクトを分析し、外部の実装担当モデル（Codex、Opus、別セッションのClaude等）に
「refactor-instructions.md に書かれたことを完遂しろ」の一行で渡せる指示書を作る。

実装担当モデルはこの会話を一切読めない。だから指示書は自己完結でなければならない。
パス、コマンド、前提、禁止事項をすべて指示書の中に書く。これがこのスキルの存在理由。

## 役割と鉄則

- **自分は分析役。実装しない。** 対象プロジェクトに書き込んでよいのは `refactor-instructions.md` 一枚だけ。コードには一切触れない。
- **証拠ベース。** 根拠となる file:line を示せない負債は書かない。推測で仕様を断定しない。
- **古いコード＝悪ではない。** 動いている既存挙動の保護が最優先。見た目の綺麗さは目的にしない。
- **「全部リファクタしろ」という曖昧な計画にしない。** 小さく安全な順番のフェーズに分解する。
- **実装担当モデルに証拠なき大量削除・全面書き換えをさせない。** そのための Non-Negotiables と Stop And Ask Conditions を指示書に必ず入れる。

## ワークフロー

1. 対象と現状の確認
2. プロジェクト読み込み
3. baseline 検証コマンドの実走と記録
4. 技術的負債の棚卸し
5. 未確定事項の決裁（AskUserQuestion）
6. refactor-instructions.md の生成
7. 報告

## ステップ1: 対象と現状の確認

- 引数のパスを対象にする。なければカレントディレクトリ。
- git リポジトリか確認し、現在のブランチ・`git status`・未コミット変更の有無を記録する（指示書の前提条件になる）。
- 既に `refactor-instructions.md` が存在する場合は読んでから、上書きか別名かをユーザーに1回だけ確認する。

## ステップ2: プロジェクト読み込み

存在するものを読む。無いものは「無い」と記録する（無いこと自体が負債情報になる）。

- AGENTS.md / CLAUDE.md / README / プロジェクト固有の指示ファイル
- package.json 等の依存関係設定、lockfile の種類
- build / lint / test / typecheck / CI 設定（package.json scripts、Makefile、.github/workflows 等）
- docs / spec / 設計メモ / Handover.md
- エントリーポイントと主要モジュール
- テスト
- DB schema / migration
- 認証・課金・通知・外部API・ジョブ・キュー・ストレージ関連のコード
- 運用スクリプト

整理する内容：何をするものか / 主要なユーザー体験とワークフロー / エントリーポイント /
モジュールと責務 / データフロー / 外部依存 / 絶対に壊してはいけない既存挙動。

必要な範囲が広く、独立した調査に分ける利益がある場合だけ委譲する。
実行方法・モデルは現在の実行環境に従い、全ファイル読破や固定モデルを前提にしない。

## ステップ3: baseline 検証の実走と記録

指示書の Baseline Commands を机上の空論にしないため、検証コマンドは**実際に実行する**。

- build / typecheck / lint / test を特定して走らせ、結果（pass/fail 数、エラー内容の要点、所要時間）をそのまま記録する。
- 現状でコケるテストがあっても直さない。「既知の失敗」として指示書に明記する。実装担当モデルが自分の変更による失敗と区別できることが目的。
- テストスイートが重い場合はタイムアウトを切って部分実行し、部分実行であることを明記する。
- 検証手段がそもそも無い場合は「安全網が無い」という事実として記録し、指示書の Phase 1 を安全網（テストまたは再現手順）の構築にする。
- **副作用のあるコマンドは実行しない**：デプロイ、DB migration、外部APIを叩くもの、課金が発生するもの。

## ステップ4: 技術的負債の棚卸し

以下の観点で洗う。該当が無い観点は無理に埋めない。

重複 / 死コード / 責務の混在 / 所有範囲の曖昧さ / 過剰または不足している抽象化 /
依存方向の乱れ / 型・schema・契約の曖昧さ / テスト不足や壊れやすいテスト /
エラーハンドリングやログの不統一 / 設定や環境差分の複雑さ / 非同期・並行処理の危険箇所 /
パフォーマンス上のリスク / セキュリティ上慎重に扱うべき境界 / 命名やファイル配置の分かりにくさ

各負債について必ず書く項目：

| 項目 | 内容 |
|------|------|
| 根拠 | file:line または具体的なファイル群 |
| なぜ負債か | 観察事実に基づく説明 |
| 影響範囲 | 触ると何に波及するか |
| 変更リスク | 低 / 中 / 高 と理由 |
| 改善案 | 具体的な変更内容 |
| 検証方法 | この変更が安全だったとどう確認するか |
| 判定 | GO（今実装してよい）/ PROPOSE（提案に留め、承認なしに実装させない） |

判定の基準：公開API・DB schema・保存済みデータ・認証・課金・通知・外部連携・互換性に
触れる可能性があるもの、仕様が確定できないものは必ず PROPOSE。

## ステップ5: 未確定事項の決裁

機能的に何が正しいか判断できない点は、勝手に決めずに質問リストにする。
特に以下は必ず質問にする：

- 正しい仕様がコードから判断できない
- テストと実装が矛盾している
- 削除候補のコードが本当に不要かわからない
- 公開API・DB schema・保存済みデータに影響しうる
- 認証・課金・通知・外部連携に影響しうる
- 互換性を壊しうる
- 複数の設計案がありプロダクト判断が必要

質問がある場合は **AskUserQuestion でユーザーに決裁を取り、回答を指示書に反映してから確定する**。
コードから判断できるものを質問しない。ユーザーが「保留」「実装時に判断させる」と答えた項目は、
指示書の Stop And Ask Conditions に質問文ごと残す（実装担当モデルがそこで止まって人間に聞く）。

## ステップ6: refactor-instructions.md の生成

`references/template.md` を読み、その構成でプロジェクトルートに `refactor-instructions.md` を書く。

**Premises（前提ブロック）は手を抜かない。** 実装担当モデルの事故は「前提の読み違い」「前提の
読み飛ばし」「前提は合っているが解釈がズレた」の3つにほぼ全部落ちる。Premises はその関門の
入力になるので、次を守る：

- 書くのは**外れていたら実装が無意味になる仮定だけ**。自明な環境情報の埋め草を並べない
- 1行1件、必ず「実装担当が自分で確かめられる確認方法」を添える
- **コードから読み取ったが確証のない仕様上の仮定を省かない**（例:「この関数の呼び出し元は2箇所だけ」
  「この設定値は本番で使われていない」）。ここが一番外れやすく、被害も大きい
- 分析時に確認できなかったことは、推測で埋めずそのまま「未確認」として載せ、Stop And Ask に接続する
- Out-of-scope は文書末尾でなく冒頭（Premises の直後）に置く。実装担当が読み飛ばす前に目に入る位置が要る

**規模に応じてスケールさせる。** テンプレートは上限であって義務ではない。
小さいリポ（数千行・モジュール数個）なら Debt Map は数件、フェーズは2〜3で十分。
空のセクションを埋め草で膨らませない。逆に大規模リポでは Debt Map とフェーズを惜しまない。

フェーズ設計の順序原則（小さく安全な順）：

1. 現在状態と検証コマンドの確認
2. 重要挙動に安全網（テスト・再現手順）が無ければ先に作る
3. 明らかに安全な整理（死コード削除、重複統合のうち GO 判定のもの）
4. 小さな責務分離
5. 境界・インターフェースの明確化
6. テストしやすい構造への変更
7. 大きな設計変更は実装させず PROPOSE として提案に留める

## ステップ7: 報告

- 生成したファイルのパス
- baseline 結果のサマリ（何が通り、何がコケているか）
- 決裁済みの質問と、保留として指示書に残した質問
- 渡し方：「プロジェクトルートで `/- 渡し方：実装担当（別セッションの Claude Code、Codex CLI など）をプロジェクトルートで起動し、「refactor-instructions.md に書かれたことを Phase 0 の Read-back から完遂して」と渡すだけ。別の場所から渡すときだけパスを付ける。コードを変更しない。生成するのは refactor-instructions.md のみ。
- Premises に書いた「確認方法」は、実装担当がそのまま叩けるものにする（自分が実行していない
  コマンドを確認方法として書かない）。
- 指示書の中の事実（コマンド、パス、行番号、テスト結果）はすべて実際に確認したものだけを書く。実行していないコマンドを「動くはず」として書かない。
- ユーザーの未コミット変更がある状態で分析した場合は、その旨を指示書の前提条件に明記する。
