# refactor-instructions.md テンプレート

このテンプレートの構成・セクション順で出力する。各セクションの下の説明文は書き方のガイドであり、
出力には含めない。`<>` 内は実際の内容に置き換える。

規模に応じてスケールさせること。小規模プロジェクトでは Debt Map 数件・フェーズ2〜3で十分。
セクション自体は全部残す（実装担当モデルが「無い」ことと「書き忘れ」を区別できるように、
該当なしのセクションには「該当なし」と明記する）。

**Premises と Out-of-scope を先頭に置くのは意図的**である。実装担当モデル（特に Codex 系）は
自分が最初に組み立てた文脈に強く引かれ、事故の大半は「前提の読み違い」「前提の読み飛ばし」
「前提は合っているが解釈がズレた」の3つに落ちる。コードが1行も出ていない時点で人間が
それを捕まえられるよう、前提を検証可能な形で冒頭に置き、Phase 0 で復唱（Read-back）させる。

Premises の書き方：**外れていたら実装が無意味になる仮定だけ**を、1行1件・検証方法つきで書く。
特に「コードから読み取ったが確証はない仕様上の仮定」（P4 相当）を省かないこと。ここが
いちばん外れやすく、いちばん被害が大きい。自明な環境情報を埋め草で並べない。

---

```markdown
# Refactor Instructions: <プロジェクト名>

> この文書は分析担当モデルが <日付> に生成した。実装担当モデルはこの文書だけを頼りに作業する。
> 不明点があれば Stop And Ask Conditions に従って止まり、人間に質問すること。
> **作業はまず Phase 0 の Read-back（前提の復唱）から始める。コードはその後。**

## Premises（前提 — 実装前に1件ずつ検証すること）

<この文書が正しく機能するために真でなければならない仮定を列挙する。
各行に「確認方法」を必ず添える。実装担当モデルは Phase 0 でこれを1件ずつ検証し、
一致／相違を Read-back で報告する。相違があった場合、その項目に依存する作業には入らない。>

| # | 前提 | 確認方法 | 外れていたら |
|---|------|----------|--------------|
| P1 | <リポジトリの絶対パス・作業の基点ブランチ・HEAD の SHA・未コミット変更の有無> | `git status` / `git rev-parse --short HEAD` | 止まって Read-back で報告 |
| P2 | <実行環境：ランタイムとバージョン、パッケージマネージャ、必要な env、ネットワーク遮断の有無> | <確認コマンド> | <行動> |
| P3 | <検証手段が動くこと（Baseline Commands が実行可能で、既知の失敗以外は通る）> | Baseline Commands の実走 | 止まって Read-back で報告 |
| P4 | <**コードから読み取ったが確証のない仕様上の仮定**。例:「この関数の呼び出し元は A と B の2箇所だけ」「この設定値は本番で使われていない」> | <grep やテストなど、実装担当が自分で確かめられる方法> | 止まって Stop And Ask |
| P5 | <分析時に確認できなかったこと・観測していないこと> | <確認方法。無ければ「確認手段なし」と書く> | 推測で埋めず Stop And Ask |

## Out-of-scope（やらんこと）

<今回触らないものを明示する。実装担当モデルはここに挙がったファイル・領域を変更してはならない。
Read-back で「触る予定のファイル」にここのものが混じっていたら、発注側が差し戻す。例：>

- <意図的な設計判断であり、バグと誤認して「直し」てはいけないもの（根拠の file:line つき）>
- <別PRに分けるべき大きな変更>
- <依存パッケージのアップグレード>
- <分析中に見つけたが今回のコースに関係しない負債>

## Objective

<このリファクタリングで達成したいことを3〜5行で。
「既存仕様を壊さず、〜の負債を減らし、今後〜を変更しやすい状態にする」の形。
見た目の綺麗さや全面書き換えは目的でないことを明記する。>

## Project Understanding

<実装担当モデルがコンテキストゼロから入れるよう、以下を簡潔に書く：>

- **What**: <このプロジェクトは何をするものか>
- **Users / Workflow**: <主要なユーザー体験・ワークフロー>
- **Entry Points**: <エントリーポイントのファイルパス>
- **Modules**: <主要モジュールと責務（パス付き）>
- **Data Flow**: <データがどう流れるか>
- **External Dependencies**: <外部API、DB、サービス、課金が絡むもの>

## Behaviors To Preserve

<絶対に壊してはいけない既存挙動を列挙する。それぞれ「どう確認できるか」を添える。
例: 「`npm run dist:client <id>` で未署名DMGが生成される（確認: ビルド後に dist/ を見る）」>

## Non-Negotiables

実装担当モデルへの絶対条件：

- **Phase 0 の Read-back を出すまでコードを1行も書かない**
- 作業開始前に必ず `git status` を確認する
- 既存の未コミット変更と自分の変更を混ぜない
  <未コミット変更がある場合はここに具体的に列挙し、触らないよう指示する>
- 編集を始める前に Baseline Commands を自分でも実行し、結果を記録する
- 変更は小さく、戻しやすい単位で行う（フェーズごと、できれば論理単位ごとにコミット）
- 無関係な整形・ついでのリファクタリングをしない
- 既存挙動を勝手に変えない
- Out-of-scope に挙がったファイル・領域を変更しない
- PROPOSE と書かれた項目を承認なしに実装しない
- 証拠なく大量削除・全面書き換えをしない
- main/master へ直接 push しない（ブランチを切る）

## Stop And Ask Conditions

以下に当たったら実装を止めて人間に質問すること：

- **Premises のいずれかが実際と相違していたとき**（その前提に依存する作業には入らない）
- 正しさが仕様から判断できない変更に踏み込みそうになったとき
- テストと実装が矛盾しており、どちらが正かわからないとき
- 公開API・DB schema・保存済みデータ・認証・課金・通知・外部連携に影響が及びそうなとき
- Baseline で通っていたテストが自分の変更で落ち、原因が30分調べてもわからないとき
- <分析時に保留になった質問があれば、質問文ごとここに列挙する>

## Baseline Commands

分析担当が <日付> に実際に実行した結果。作業前に同じコマンドを実行し、同じ状態であることを確認すること。

| コマンド | 結果 | 備考 |
|----------|------|------|
| <例: `npm run typecheck`> | <pass / fail（エラーN件）> | <所要時間、部分実行の有無> |
| <例: `npm test`> | <N passed, M failed> | <既知の失敗はテスト名を列挙> |

<既知の失敗がある場合: 「以下のテストは現状でも失敗している。直す必要はないが、これ以外を新たに落とさないこと」>
<検証手段が無い場合: 「このプロジェクトには自動検証が無い。Phase 1 で安全網を作ることが最初の作業である」>

## Debt Map

<棚卸しした負債を、判定（GO / PROPOSE）付きで列挙する。各項目の形式：>

### D1: <負債の短いタイトル> — GO | PROPOSE

- **根拠**: <file:line または対象ファイル群>
- **問題**: <なぜ負債か。観察事実ベースで>
- **影響範囲**: <触ると何に波及するか>
- **変更リスク**: <低/中/高と理由>
- **改善案**: <具体的な変更内容>
- **検証**: <安全だったとどう確認するか>

## Implementation Phases

<小さく安全な順。各フェーズは独立して検証・コミットできる単位にする。
対応する Debt Map の番号（D1, D2...）を参照する。PROPOSE 項目はフェーズに入れず、
最終フェーズの「提案のみ」にまとめる。>

### Phase 0: 現状確認と Read-back（前提の復唱）

1. `git status` を確認し、作業ブランチ <ブランチ名の指定> を切る
2. Baseline Commands を全て実行し、結果をこの文書の表と突き合わせて記録する
3. **Premises を P1 から1件ずつ確認方法どおりに検証する**
4. **Read-back を出す。これを出すまでコードを1行も書かない。** 内容：
   - Premises 各行の判定（一致 / 相違。相違なら実際に観測した値）
   - Baseline 実走結果と、この文書の表との差異
   - Objective を自分の言葉で1行に言い直したもの
   - Out-of-scope を自分の言葉で1行に言い直したもの
   - **これから触る予定のファイル・モジュールの一覧**（フェーズごと）
   - **今回触らないと約束するもの**
   - 要件の解釈が複数に割れた点と、自分の推奨（あれば）
5. Read-back の宛先と待ち方は発注側の指示に従う。指示が無ければ、Read-back を最初の出力として
   提示してから進む
6. Premises に相違がある、または解釈が割れている場合は Phase 1 に進まず Stop And Ask

### Phase 1: <安全網の構築（必要な場合）>

<対象: D__。何のテスト・再現手順を作るか。完了条件。>

### Phase 2: <明らかに安全な整理>

<対象: D__。完了条件と検証コマンド。>

### Phase N: <...>

### Final Phase: 提案のみ（実装禁止）

<PROPOSE 判定の項目について、実装せず提案書（箇条書きで可）を report に含めること。>

## Verification Requirements

- 各フェーズの完了時に Baseline Commands を再実行し、baseline から劣化していないことを確認する
- <プロジェクト固有の検証があれば追記。例: 起動確認、特定の手動手順>
- 全フェーズ完了後、最終確認として <最重要の検証手順> を実行する

## Reporting Format

作業完了時に以下を報告すること：

1. **Phase 0 の Read-back 全文**（発注側から訂正を受けた場合は、訂正内容と反映結果も）
2. 何をしたか（フェーズごとに簡潔に）
3. 変更したファイル一覧（Read-back で申告した「触る予定」との差分があれば理由を添える）
4. 最後に実行した検証コマンドとその結果（コピペで）
5. 実装しなかった PROPOSE 項目への提案
6. Stop And Ask で止まった点・未解決の点
```
